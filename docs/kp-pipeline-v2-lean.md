# КП-конвейер v2 (lean)

После критики v1. Удалено всё, что не нужно для решения «работает / не работает» за 6 недель.

## Главный сдвиг

**v1 продавал архитектуру.** Четыре слоя, 5 шагов, 16 tools, 4 скилла, MCP-сервер как фундамент, 6 спринтов.

**v2 продаёт результат за 6 недель на одном поставщике.** Никакой MCP-сервер в MVP — это batch-пайплайн, ему MCP не нужен. Никаких embeddings до момента, когда fuzzy объективно сломается. Один промпт, один скрипт, одна Smart-Process с тремя стадиями.

## Что строим (MVP, 6 недель)

```
Excel/PDF от ОДНОГО поставщика
        ↓ Python-скрипт (cron или вебхук на email)
        ↓ парсинг таблицы → JSON позиций
        ↓ матчинг с каталогом БУС: SKU + fuzzy по названию
        ↓ три флага: new_sku / price_anomaly / ambiguous_match
Карточка Smart-Process «Входящее КП» в Б24
        ↓ оператор: «Принять» / «Посмотреть» (две корзины)
Триггер на «Утверждено» → сделка в CRM
```

**Всё.** Никаких vision-сканов, Telegram-ботов, semantic_search, генерации писем поставщикам через MCP, скиллов как отдельных артефактов, аналитики обучения.

## Архитектура (одна страница)

### Данные
- **Поставщик** — карточка CRM (контакт/компания)
- **Входящее КП** — Smart-Process. Поля: исходный файл, JSON позиций, статус, сводка проблем, оператор
- **Позиция** — связанный элемент с полями: supplier_name, qty, price, matched_product_id, confidence, flag

### Пайплайн (3 шага, не 5)
| Шаг | Делает | Артефакт |
|---|---|---|
| **A. Парсинг** | Скрипт извлекает таблицу из Excel/PDF (только цифровой PDF). Промпт LLM нормализует колонки (артикул/код/SKU → один формат) | JSON списка позиций |
| **B. Матчинг + флаги** | По каждой позиции: `find_by_sku` точное → если нет, `fuzzy_search` по названию (порог 0.85 = зелёный, ниже = `ambiguous_match`). Сверка цены с историей: отклонение >25% = `price_anomaly`. Нет в каталоге = `new_sku` | Список позиций с флагами |
| **C. Сборка в Б24** | REST-вызов: создать карточку Smart-Process + позиции | Оператор получает уведомление |

### Smart-Process: три стадии
**Новое → Утверждено → Архив.** Всё. Оператор открывает «Новое», работает, нажимает «Утвердить». Дополнительные стадии («На проверке», «Отклонено») добавятся, когда оператор сам попросит.

### UX оператора: две корзины
- **«Принять»** — позиции с зелёным матчем без флагов. Свёрнуты в группу «N позиций ОК».
- **«Посмотреть»** — всё остальное (любой флаг). Каждая позиция отдельно с пояснением.

Оператор может: переназначить товар из каталога inline, отметить «не берём», создать новую карточку товара (для `new_sku`). Bulk-действие одно: «Принять все ОК».

## Что выкинуто и почему

| Удалено | Почему |
|---|---|
| MCP-сервер для пайплайна | Это batch, не чат. MCP оправдан, когда оператор спрашивает в чате «найди похожие КП». Это feature позже, не MVP |
| `semantic_search_product` (embeddings) | Векторная БД, переиндексация, отдельные evals. Fuzzy + LLM-нормализация колонок покрывает 90% реальности |
| `propose_supplier_email` как MCP tool | Это LLM-вызов из UI, не tool. Кнопка в карточке → Claude API → черновик письма |
| Vision для PDF-сканов | До замера % сканов в реальных КП клиента — нельзя оценить экономику. Backlog |
| Telegram-бот | В пилоте email-ящик `kp@клиент` + ручная загрузка из Б24 — достаточно |
| 4 отдельных скилла | Один системный промпт. Декомпозиция после 100+ КП |
| Флаги `duplicate_in_kp`, `unit_mismatch`, `obsolete` | Реже 1 раза на 50 КП. Обрабатываются глазами за секунду |
| Поля `source_channel`, `parser_version`, `auto_publishable` | Фантазии о зрелой системе |
| Evalite + DeepSeek в MVP | 10 размеченных КП в JSON + pytest. Evalite — на 2-м клиенте |
| Спринт 5 (аналитика, supplier mapping training) | Пост-MVP |
| «6 типов поставщиков, 30 КП» как цель пилота | Один поставщик, один формат, 10 КП. Сначала самый частый случай |

## Discovery — 5 вопросов вместо 24

До подписания контракта нужны ответы только на эти:

1. **Сколько КП в неделю / месяц?** Меньше 5/нед = автоматизация не отбивается, не делаем. Больше 20/нед — однозначно делаем.
2. **Доминирующий формат?** Excel — простой случай. PDF цифровой — средний. PDF-скан — фактически другой проект.
3. **Бюджет на LLM в месяц?** Оценка из шапки: ~$0.30–0.50 на КП. При 100 КП/мес — $30–50. Допустимо?
4. **Можно в облачную LLM или только on-prem?** КП — конфиденциально. Это меняет стек радикально.
5. **Кто оператор и есть ли у него Б24 сейчас?** Если оператор не живёт в Б24 — Smart-Process теряет половину УТП.

Остальные 19 вопросов закрываются по ходу гипотезами. Если гипотеза неверна — откатываем на discovery.

## Экономика (на основе которой вообще решаем браться)

**Прикидка от критика, проверенная:**
- LLM на 1 КП (50 позиций): ~$0.30–0.50
- Менеджер в СНГ: ~$1000/мес = ~$6/час
- Если КП обрабатывается вручную за 1 час, автоматически — за 5 минут, экономия = ~$5.50 за КП минус $0.50 LLM = **~$5 чистой экономии на КП**

**Точка безубыточности по разработке** (грубо $10–15K за пилот): **2000–3000 обработанных КП**. При 100 КП/мес — 2 года. При 500 КП/мес — 4–6 месяцев.

**Вывод:** проект имеет смысл только при потоке >100 КП/мес у одного клиента, или при тиражировании на 5+ клиентов. Это не «продукт», это **услуга с воспроизводимым каркасом**. Честно так и продавать.

## Что я НЕ принял из критики (с аргументацией)

**1. «Убери КП, оставь только Look».** Не принято. Look продаётся через Wow-эффект (генерация картинок), но **Look — это marketing tool в нише fashion-ритейла**. КП — это **closed-loop экономия в любом b2b с поставщиками**. Это разные рынки. Look — emotional buy (зацепить и вирус), КП — rational buy (считается калькулятором). Нам нужны оба: Look — для входа и демо, КП — для контрактов с ROI. Снимать КП нельзя, можно отсрочить продажу.

**2. «Smart-Process — не очевидный выбор, можно вкладку в сделке».** Не принято. Вкладка в сделке = «КП — часть закупки», что неверно онтологически: одно КП может породить 0, 1 или несколько сделок (или ни одной, если отклонено). Smart-Process = самостоятельный жизненный цикл с собственной воронкой, отчётами, правами. Это правильное архитектурное решение, не привычка. Соглашусь только в одном: **3 стадии вместо 6** — да, упрощаем.

**3. «MCP-сервер вообще не нужен в пилоте».** Принято частично. В пилоте КП-конвейера MCP действительно не нужен — это batch. Но MCP остаётся как **второй слой того же продукта**: чат-режим оператора («покажи все КП от этого поставщика за квартал», «найди похожие проблемы»). В коммуникации с клиентом это правильно подавать как **этап 2 после пилота**, а не как часть MVP. Так и переписываю.

## Что осталось от УТП после критики

Было:
> «AI-конвейеры с оператором-в-цикле, встроенные в Битрикс24 через Smart-Process + MCP».

Стало (честнее и уже):
> «Автоматизация рутины в Битрикс24 через Smart-Process и AI. Конкретно: КП от поставщиков → готовая сделка с разобранными проблемами. Look-сборка из каталога → опубликованная страница с hero-картинкой. Чат-доступ к данным — следующий слой после пилота».

Различия:
- Убрано слово «конвейеры» (слишком абстрактно) → «автоматизация рутины»
- Убран MCP из главного слогана → перенесён в «следующий слой»
- Конкретика двух кейсов прямо в УТП — клиент сразу видит, что это и сколько стоит

## Финальная честность

Критик прав в главном: **v1 был продажным документом архитектора, который любит свою архитектуру**. v2 — это документ инженера, который знает, что 80% написанного выкинется при первом контакте с реальностью, поэтому пишет только те 20%, которые точно нужны для решения «работает / не работает».

Это и есть применение первых принципов. Хорошо, что субагент об этом напомнил.
