# КП-конвейер для Битрикс24

Автоматическое внесение коммерческих предложений от поставщиков в Б24.
Описание подхода, технологический контур, пилотный кейс.
Документ для согласования с заказчиком. Версия 1.

## 1. Краткое резюме

Поставщики присылают коммерческие предложения (КП) в произвольном формате — PDF, Excel, Word, иногда фото или скан. Менеджер по закупкам тратит от 20 минут до нескольких часов на одно КП: распознать позиции, сопоставить с каталогом, сверить цены, отметить расхождения, завести сделку.

**Бизнес-эффект:** время на обработку одного КП сокращается до 1–3 минут оператора. AI делает черновую работу (распознавание, матчинг, поиск аномалий), оператор открывает в Б24 готовую сделку с подсвеченными проблемами и принимает решение.

**Технически КП = Smart-Process «Входящее КП» в Б24** с привязанными товарами через UF-поля и стадиями согласования. На стадии «Утверждено» триггер создаёт сделку и/или обновляет каталог через MCP/REST.

**Конвейер автоматизирован AI:** входящий файл → парсинг → нормализация → MCP-матчинг с каталогом БУС/Б24 → сборка карточки в Smart-Process с флагами проблем → оператор согласует → исполнение.

> **Главная гипотеза пилота:** на 30 реальных КП от трёх типов поставщиков (с прайс-листом, с одноразовыми позициями, со смешанным составом) AI-матчинг достигает ≥85% точности на «уверенных» позициях, остальные 15% явно отмечены как требующие ручной проверки. До пилота — это гипотеза, не обещание.

## 2. Архитектура решения

Четыре слоя, та же модель, что и в Look-конвейере.

### 2.1. Данные и онтология (в Б24 + БУС)

- **Поставщик** — карточка в CRM (контакт/компания), связана с КП.
- **Входящее КП** — Smart-процесс в Б24. Хранит исходный файл, распознанный JSON, статус, привязки.
- **Позиция КП** — строка из КП. Поля: `supplier_sku`, `supplier_name`, `qty`, `price`, `currency`, `unit`, `raw_text`, плюс результаты матчинга: `matched_product_id`, `confidence`, `flags[]`.
- **Товар** — карточка в БУС (та же, что в Look). Опционально — кросс-таблица «Поставщик ↔ Товар» с историей цен.
- **Проблема** — типизированный флаг на позиции. Закрытый список: `new_sku` (нет в каталоге), `price_anomaly` (отклонение от средней закупки >X%), `ambiguous_match` (модель уверена <70%), `unit_mismatch` (поставщик в шт, у нас в упаковках), `obsolete` (товар снят с продажи), `duplicate_in_kp` (одна позиция дважды в одном КП).

Дополнительные свойства КП:
- `source_channel` — email / Telegram / ручная загрузка
- `parser_version` — какая версия пайплайна обработала
- `confidence_overall` — агрегированная уверенность по всем позициям
- `auto_publishable` — флаг «все позиции зелёные, можно публиковать без человека» (на этапе зрелости системы)

### 2.2. Производственный конвейер (5 шагов)

| Шаг | Что происходит | Инструмент | Артефакт |
|---|---|---|---|
| **A. Приём** | Принимаем файл из email / Telegram-бота / Б24-Drive | Email-коннектор + webhook в MCP | Файл + метаданные источника |
| **B. Парсинг** | Распознаём содержимое: таблицы, текст, числа, единицы измерения. PDF/Excel/Word/изображение → структурированный JSON | Скилл `kp-parsing` + LLM с vision + Tabula/openpyxl для табличных | JSON со списком позиций (supplier_sku, name, qty, price, ...) |
| **C. Матчинг** | По каждой позиции — найти в нашем каталоге. Сначала точные совпадения по SKU/штрихкоду, потом нечёткие по названию, потом семантические через embeddings | MCP `mysport-catalog` (tools: `find_by_sku`, `find_by_barcode`, `fuzzy_search`, `semantic_search`) + скилл `kp-matching` | Список позиций с `matched_product_id` и `confidence` |
| **D. Анализ проблем** | Каждая позиция прогоняется через правила: новизна, ценовая аномалия, дубль, неоднозначность. Скилл генерирует короткие пояснения «почему флаг» | Скилл `kp-anomaly` + MCP `get_price_history` | Флаги + пояснения по каждой позиции |
| **E. Сборка в Б24** | Создаётся карточка Smart-Process «Входящее КП», позиции прикрепляются как связанные элементы, проблемы — в отдельном табе. Оператор получает уведомление | MCP tools: `create_kp`, `attach_positions`, `notify_operator` | Готовая карточка в Б24, оператор работает в привычном UI |

### 2.3. Согласование (Smart-Process «Входящее КП» в Б24)

Стадии:
- **Новое** — система создала, оператор ещё не открывал
- **На проверке** — оператор работает с позициями (раскрывает спорные, мапит вручную, дополняет каталог)
- **Готово к решению** — все позиции либо смаплены, либо явно помечены «не берём»
- **Утверждено** → триггер: создание сделки в CRM + обновление цен поставщика в кросс-таблице
- **Отклонено** → причина фиксируется в карточке, статистика идёт в аналитику
- **Архив**

Поля карточки:
- Бриф (краткое summary КП — кем, сколько позиций, общая сумма)
- Состав (UF-привязка к позициям)
- Файл-оригинал
- Сводка проблем (счётчики флагов)
- Комментарий оператора
- Метрики (время на обработку, итоговая уверенность)

### 2.4. UX оператора в Б24

Оператор видит **одну карточку**, в ней:
- **Светофор позиций.** Зелёные (точный матч + нет аномалий) — свернуты в группу «N позиций ОК, развернуть». Жёлтые (есть флаг) — каждая отдельной строкой с пояснением. Красные (нет матча или критическая аномалия) — наверху, требуют действия.
- **Bulk-действия.** «Принять все зелёные», «Создать карточки в каталоге для всех красных new_sku», «Запросить разъяснение у поставщика по жёлтым» (генерирует письмо).
- **Inline-редактирование.** Кликнул на позицию → выбрал правильный товар из каталога → confidence пересчитался.
- **История поставщика.** Свернутый блок «Этот поставщик присылал N КП за полгода, средняя цена по топ-10 позициям такая-то».

## 3. Технологический стек

### 3.1. MCP-сервер `kp-catalog` (расширение `templates-mcp`)

Те же 31 базовый tool из `templates-mcp` + новые tools под этот домен:

**Парсинг и приём:**
- `parse_kp_file` — принимает file_id, возвращает JSON позиций
- `extract_kp_metadata` — поставщик, дата, контакт, валюта

**Матчинг:**
- `find_product_by_sku` — точный поиск по нашему SKU
- `find_product_by_barcode` — точный по штрихкоду
- `find_product_by_supplier_sku` — поиск по SKU поставщика (если знаем мэппинг)
- `fuzzy_search_product` — нечёткий по названию (Levenshtein + token-based)
- `semantic_search_product` — embeddings-based, для случаев «другая формулировка того же товара»
- `get_supplier_product_mapping` / `set_supplier_product_mapping` — обучаем систему на исправлениях оператора

**Аналитика:**
- `get_price_history` — история закупочных цен по товару
- `get_supplier_stats` — статистика по поставщику (средние цены, типичные позиции, частота КП)
- `check_unit_consistency` — единицы измерения совпадают?

**Сборка в Б24:**
- `create_kp_smart_process` — создать карточку
- `attach_kp_positions` — прикрепить позиции
- `flag_position` — поставить флаг с пояснением
- `propose_supplier_email` — сгенерировать письмо поставщику с вопросами

### 3.2. Скиллы Claude

- **`kp-parsing`** — как извлекать табличные данные из разных форматов. Правила распознавания заголовков, единиц измерения, валют, разделителей. Шаблоны промптов для vision-режима на сканах.
- **`kp-matching`** — пайплайн матчинга. Сначала точные совпадения (если SKU/штрихкод есть — берём), потом fuzzy (порог уверенности), потом semantic. Правило «никогда не выдавать ложноположительный матч, лучше пометить как ambiguous».
- **`kp-anomaly`** — что считать аномалией. Пороги отклонений по категориям, признаки «дубль в КП», правила про единицы измерения.
- **`kp-supplier-comm`** — как формулировать вопросы поставщику. Tone of voice, что нельзя писать (не раскрываем внутренние цены), шаблоны ответов.

### 3.3. Парсинг файлов

- **PDF с текстовым слоем** → pdftotext + LLM для интерпретации структуры
- **PDF-скан** → vision-модель (Claude / Gemini) с промптом из `kp-parsing`
- **Excel** → openpyxl, выгрузка как таблицы + LLM для маппинга колонок
- **Word** → docx2txt + LLM
- **Изображения (фото)** → vision-модель

LLM нужна **не для извлечения данных как таковых**, а для **маппинга разнородной структуры в нашу единую схему**. У одного поставщика «Артикул», у другого «Код», у третьего «№». Регулярки тут не выживают — LLM выживает.

### 3.4. Источники файлов

- Отдельный email-ящик `kp@клиент.by` — все письма автоматически парсятся
- Telegram-бот — менеджер пересылает КП в чат, бот закидывает в систему
- Загрузка вручную в Б24 (через приложение/кнопку в Smart-Process)

## 4. Поэтапный план

| Спринт | Цель | Результат |
|---|---|---|
| **0** | Сбор 20-30 реальных КП из истории клиента, разметка вручную «эталона» | Тестовый набор для evals. Понимание реальной вариативности входа |
| **1** | MCP-сервер расширен tools матчинга. `find_by_sku`, `fuzzy_search`, `semantic_search`. Скилл `kp-matching` | На разметке достигаем целевую точность матчинга (целевая planирана после спринта 0) |
| **2** | Скилл `kp-parsing` + интеграция с парсерами файлов. Smart-Process «Входящее КП» в Б24 | Конвейер от файла до карточки в Б24 на 5 пилотных КП |
| **3** | Скилл `kp-anomaly` + UI оператора (светофор, bulk-действия) | Оператор обрабатывает реальные КП через систему вместо ручного режима |
| **4** | Email-коннектор + Telegram-бот. Триггер на «Утверждено» → сделка в CRM | Полный production loop, KPI собирается |
| **5** | Аналитика, обучение на исправлениях оператора (supplier_product_mapping автонаполняется) | Точность матчинга растёт по мере использования |

## 5. Пилотный кейс (план)

Берём **одного поставщика** с регулярными КП (раз в неделю / месяц), смешанной структурой (часть постоянная номенклатура, часть разовая), исторически проблемного по матчингу. Прогоняем 10 его последних КП через систему, сравниваем с тем, что менеджер сделал руками.

Метрики пилота:
- **Точность матчинга** на «зелёных» позициях (доля корректно сопоставленных без вмешательства оператора)
- **Время обработки** одного КП (от получения файла до утверждённой сделки)
- **Полнота охвата проблем** (сколько реальных проблем система подсветила сама vs пропустила)
- **Доля КП, прошедших без правок оператора** (бенчмарк зрелости системы)

## 6. Что ещё не решено (открытые вопросы)

### Блок 1. Команда и роли
1. Кто оператор? Закупщик / категорийный менеджер / специальный человек на этой задаче?
2. Сколько КП в неделю / месяц проходит сейчас? Сколько менеджеров их обрабатывает?
3. Кто принимает финальное решение об утверждении КП — оператор или его руководитель?

### Блок 2. Поставщики и форматы
4. Сколько активных поставщиков? Сколько шлёт КП регулярно?
5. Какие форматы доминируют — Excel, PDF, что-то ещё? Есть ли «дикие» форматы (фото от руки, сканы плохого качества)?
6. Есть ли договорённость с топ-поставщиками на единый формат, или каждый по-своему?
7. Языки КП — только русский, или встречается английский / другие?

### Блок 3. Каталог и матчинг
8. Сколько SKU в каталоге БУС?
9. Как сейчас живёт связь «Поставщик ↔ Товар»? Где это хранится — в Б24, в БУС, в Excel у менеджера, в голове?
10. Есть ли штрихкоды на товарах? Шлют ли поставщики штрихкоды в КП?
11. Что считать «той же позицией» если у поставщика чуть другая фасовка (50 шт vs 100 шт того же товара)?

### Блок 4. Аномалии и пороги
12. Сколько процентов отклонения цены считать аномалией? По всем категориям одинаково или по-разному?
13. Что делать с позицией, которой нет в каталоге — автоматически заводить карточку (черновик), требовать ручного создания, или предлагать только при утверждении?
14. Дублей в одном КП — какая логика? Суммировать количество или поднимать флаг?

### Блок 5. Б24 и интеграция
15. Б24 уже используется в закупках? Есть ли там процесс работы со сделками / поставщиками?
16. Есть ли уже Smart-процессы в Б24?
17. CRM-сделка по результатам КП — это новая сделка под каждое КП, или одна сделка на поставщика, обновляющаяся?
18. Доступ к серверу БУС — можем ли разворачивать MCP-сервер на нём?
19. Хранение исходных файлов КП — Б24-Drive, отдельный S3, локальная папка?

### Блок 6. Юридическое и безопасность
20. КП от поставщиков — конфиденциально? Нужно ли всё хранить on-prem или допустимо отправлять в облачную LLM?
21. Audit log — нужен ли отдельный журнал действий оператора и системы для контроля?

### Блок 7. Запуск и пилот
22. Какой поставщик идёт в пилот первым? Идеально — частые КП, средняя сложность, кооперативный менеджер.
23. Срок MVP? Срок production?
24. Бюджет на LLM-вызовы — на vision-парсинг тратится больше всего, важно оценить помесячно.

## Что общего с Look-конвейером

Та же четырёхслойная архитектура:
- **Данные/онтология** — расширение того же каталога БУС, та же модель «карточка + связи»
- **AI-конвейер** — те же 5 шагов (вход → разбор → матчинг → проблематизация → сборка в Б24)
- **Smart-Process** — та же роль «UI оператора в привычной среде»
- **MCP-сервер** — тот же фундамент `templates-mcp` + предметные tools

Это подтверждает воспроизводимость схемы: третий конвейер (база знаний через чат) пишется ещё быстрее, потому что слой «оператор-в-цикле» можно сделать опциональным.
